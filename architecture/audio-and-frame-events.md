# Gameplay buff observations versus audible playback

**Status (updated 2026-10-13):** TFM2 **0.6.3 / stable ABI 9**; runtime evidence through **Berserker Probe 016 / mod v0.0.12**. **Verified:** custom WAV playback on visible HUD time, independent owned WinMM voice interruption with ordinary game audio continuing in Probe 008, Rage-candidate-driven file-backed WAV audio with pause-through-clip/title cleanup in Probe 015, and **same-Rage continuation across short WAV files without audible gaps or overlap in Probe 016**. **Unresolved:** exact native presentation cursor/cast-start event, confirmed death timing, faster-speed frame accuracy, replay seek, master-mute/gain mapping, simultaneous-instance test, and forced DLL unload.

**Additional current evidence (2026-10-14):** an exact-build **TFM2 0.6.4 / ABI 10** owner run now physically verified Candidate-A observer execution, owned-WAV Rage chaining, one in-Rage stable-player death and a silent `would_preempt_rage` HUD decision. See 0.6.4 section below. The 0.6.3 claims above remain historical and build-specific.

## Simulation state is not the playback clock

Berserker's observed `berserker_skill1` buff repeatedly lasted exactly **179 simulation ticks** for naturally completed intervals. Probe 006 recorded **91 additions**, **88 normal removals**, and three disappearances while the buff was active. The disappearances reported nonzero previous-tick HP and `alive=true`: they are *death/despawn candidates*, not verified death events. The 179-tick buff remains a **strong Rage candidate**, not a visually cross-validated Rage identification.

Probe 002 found that watched simulation reached **36,471** (~10:08 at 60 tps) while the visible HUD was only at **00:47**. Simulation callbacks therefore cannot trigger audible clips at the observed tick without a separate presentation-time mechanism.

## Sound-event APIs are not interchangeable

**Runtime verified:** Probe 003 played a quiet mod-owned synthetic WAV via `StableClient::play_sound(path, volume)` on F8; the owner heard it. Probe 004 then played the same file through a HUD-clock-triggered `play_sound` at visible **00:10**, and the owner heard both the manual and automatic beeps. This demonstrates **coarse client presentation-time one-shot audio**, not precise replay scheduling.

**Runtime negative evidence:** Probe 003 called `StableSim::play_sfx(name, caster_id, target)` from the scheduled match hook at tick 600, but the owner could not hear the expected 00:10 sound. The official [stable API](https://github.com/teamsamoyed/TeamfightManager2Mod/blob/main/docs/stable-api-reference.md) describes `play_sfx` as a *view-effect name* that must already have a corresponding client binding. The experiment instead used a custom **file path**. That binding mismatch is a **plausible explanation, not proved exclusive cause**. It does not disprove the properly bound frame-event pipeline.

**API documentation evidence:** `play_sound` has no documented individual sound voice handle or per-voice stop operation. Do **not** assume arbitrary 3+ second sounds can be interrupted using this method. Do not hijack global `play_bgm` / `stop_bgm` for independent champion voices.

## Independent audio voices: evidence ladder

**Standalone runtime verified, 2026-10-09 (Audio Voice Probe A):** WinMM `waveOut` used two distinct handles for self-generated 440 Hz and ~659 Hz PCM tones. The tester heard two tones, then one, then silence after individual handle resets. A second standalone run with TFM2 open confirmed the same note sequence, but game-sound continuity was not explicitly reported at that stage. This was **not** an SDK-owned stop API or XAudio2.

**In-process runtime verified, 2026-10-09 (Berserker Probe 007, v0.0.7):** In TFM2 0.6.3, the mod client's explicit F10 test started two synthetic WinMM voices; callback stop requests occurred at **903 ms** and **2105 ms**, and the tester heard the two-to-one-to-silence sequence. This proved in-process independent sound stopping, but not that the game's original audio continued unaltered.

**Manual interruption + native sound coexistence verified, 2026-10-11 (Berserker Probe 008, v0.0.8):** The user heard **two successful F10 start-both → stop-low-only → stop-high sequences**, and explicitly reported that TFM2's normal audio continued. Separate stop-request callbacks were logged at **2166/3891 ms** in the first sequence and **1756/3386 ms** in the second. No audio-error marker was reported. This is a **real in-process, game-audio-coexisting demonstration** with generated tones—not a claim of calibrated speaker latency, per-champion voice ownership, or full Rage integration.

**Further lifecycle runtime verified (2026-10-11; Berserker Probe 008, v0.0.8):** The owner confirmed two additional sound behaviors while watching TFM2 0.6.3, with matching diagnostic evidence.

- **Watchdog:** an F10 start left both WinMM voices active; without another F10, the client logged `VOICE_INPROCESS_CLEANUP reason=watchdog_8_seconds low_active=true high_active=true`. The owner heard both notes stop. The log has no calibrated speaker-out latency and no exact watchdog elapsed-ms value.
- **Title-screen exit:** in a separate run, both voices were still active when the stable-client callback logged `VOICE_INPROCESS_CLEANUP reason=left_ingame_scene low_active=true high_active=true`; immediately afterward the UI logger recorded an `InGame → Title` transition. The owner confirmed the sounds stopped while **TFM2 stayed running**.
- **Useful negative control:** an earlier exit attempt quit TFM2 to Windows while sound was active. The process stopping sound is **not evidence** of clean mod/DLL unload. That trial did not contain the positive client cleanup marker and remains inconclusive.
- **Concurrency boundary:** diagnostics from the watched simulation still continued after the title transition. A running simulation worker does **not** imply an active client match presentation. Audio teardown must be tied to the relevant client scene or playback epoch.

**Still open:** game volume/mute linkage (independent WinMM need not follow TFM2's settings), forced DLL unload/crash safety, seek/pause/speed, multiple champion voices, native Rage/death events, clip streaming and rights, measured speaker-stop latency, and XAudio2. The prior Probe 008 manual-stop run transitioned to results only **after** the sounds ended; the *later* separate return-to-title test is what establishes active-voice cleanup.

## Playback-clock UI negative experiment

- Probe 005 depth-first UI scan was **inconclusive**: it exhausted 1,202 nodes / 36 matches, mostly on unrelated athlete/champion *speed* labels. Twenty-nine samples returned no slider ratios.
- Probe 006 replaced it with a bounded **breadth-first** SDK UI scan (max depth 13, 12k-node limit, 150 nodes/client update). It **drained its queue after 3,189 visited nodes** (`truncated=false`) and collected **30** subsequent samples.
- No retained candidate was a slider runner; all 30 samples had `ratios=[]`. Only the whole-second `ingame.header.game_time.value` was identified as a useful time label.
- **Scope:** no high-resolution playback cursor was found **in the UI tree exposed to this scan**. This does not prove the native replay has no fine-grained cursor or that deeper/inaccessible UI state does not exist.

## Implications and remaining tests

1. Separate presimulation tick, rendered replay cursor, monotonic wall time, scene epoch, and champion identity. The HUD's integer seconds are insufficient for a 179-tick effect's exact entry/exit.
2. Use native presentation-state investigation (exact build fingerprint and fail-closed reads) instead of repeating an unchanged UI traversal.
3. Probe 008 confirmed **two early/manual in-process WinMM stop sequences while normal game audio continued**; subsequent owner-run follow-ups confirmed **both-voice watchdog timeout and return-to-title cleanup**. Focus next on exact playback Rage/death triggers, pause/seek, and forced-unload robustness—not repeating basic two-tone feasibility. XAudio2 remains a documented, untested alternative.
4. Prove true death callback/order and multiple-Berserker handling. Despawn is not the same as an observed death.

## Third-party custom champion audio asset pipeline (static evidence, 2026-10-12)

**Status:** **static evidence only** from an uploaded copy of Workshop package `3774304166`, identified by its bundled metadata as *Silver's League of Legend Reborn* (`test_mod`, package metadata version `0.1.0`). **Game version not established:** the package includes an older minimum `base >=0.4.11` dependency and workshop-note filenames, neither of which proves an exact runtime-tested build. This package was inspected but **not installed, executed, or tested against TFM2 0.6.3**.

A custom champion's declarative effect can specify `{"type":"Sfx","name":"example_cast"}` (or `TargetSfx`). A `sound/sfx/example_cast.sound_info` file provides a `plays` array; each entry has a `clip` asset name, `delay` and `volume`. The package registers sound definitions and individual clips through `mod.override_info` mappings from `asset/base/sound/sfx/...` to `asset/<mod_id>/sound/sfx/...`. External `.wav` and `.mp3` assets exist alongside these declarations. In this snapshot there are 111 `.sound_info` entries, 98 WAV clips, 13 MP3 clips, and 206 sound-path override entries. Counts describe the archive, **not** which entries successfully play.

The `plays` array can declare multiple clips/delays for one event (example patterns include 0 and 0.15 second entries, or repeated clips). This is evidence of an authored scheduling *format*, **not** verification of playback fidelity, looping, cancellation, audio handle ownership, pause behavior, or replay synchronization.

**Relationship to Berserker probes:** earlier Probe 003's inaudible `StableSim::play_sfx` used a file path instead of a bound sound-event name; this third-party asset layout strengthens the **binding-mismatch hypothesis** but does not prove it was the exclusive cause. ## Opt-in Rage-candidate audio mapped to a coarse visible HUD clock (runtime, 2026-10-13)

**Runtime-verified partial result:** In TFM2 **0.6.3**, SDK/host **ABI 9**, Berserker Keeps Yelling **Probe 013 / mod v0.0.9**, the owner audibly observed automatic synthetic WinMM tones driven by *recorded* `berserker_skill1` watched-presimulation transitions and the visible `ingame.header.game_time.value` whole-second HUD clock. A single match log recorded **16 tone starts**, **15 normal ends**, **one forced pause-related stop**, **zero logged voice errors**. This establishes a *coarse event-to-audio proof of concept*, **not** a runtime Rage cast callback or frame-accurate synchronization. The original buff intervals remained **179 simulation ticks** for complete durations; the mod's 60-ticks-per-HUD-second mapping is still an **unverified hypothesis**.

**Negative results that other audio mods can reuse:** the owner saw audible onset **after the Rage activation animation began** (near red visual state) and cutoff roughly half a second **after redness ended**. This demonstrates that a buff active interval, HUD-time quantization, and **cast animation onset are different landmarks** and must not be conflated. The 250 ms HUD logger skipped **3–4 displayed game seconds** between samples under acceleration, potentially missing complete ≈3-second Rage intervals; playback speed is a **presentation sampling condition**, not a change to already recorded simulation ticks. The test preview's pitch changed across respawned entity IDs because the mod intentionally keyed synthetic frequency to the ID; it was **not** an effect of the game changing sounds. Escape/pause triggered the preview's own `HUD_stalled_pause_or_slow_speed` disarm, making later automatic tones unavailable without re-arming; this is a **diagnostic design bug**, not proof of an SDK F11 input defect.

**Owner-run Probe 014 update — RUNTIME-VERIFIED PARTIAL (2026-10-13, original TFM2 0.6.3, ABI 9, mod 0.0.10):** The owner compared 0.5-, 1.0- and 0.0-second early-phase settings using F7. **Both early offsets were visibly too early; zero lead best aligned sound with activation animation and red Rage state**. This **supersedes the source-only hypothesis that 0.5-second early lead would be the preferred default**. The log contains **21 synthetic tone starts, 16 ordinary stops, five forced voice cleanups, six pause suspensions, five automatic resumes and no voice errors**. All logged tones held a fixed **440 Hz** pitch; all 64 complete watched `berserker_skill1` spans remained 179 simulation ticks. A pause still caused an audio stop followed by a delayed restart after the HUD advanced; user reported the delay. The final logged pause lacks a subsequent observed resume because the log ends there. There were no rate-jump diagnostics to establish accelerated-playback fidelity. No native cast event, precise replay clock, true death event or game-mixer integration was validated.

**Reusable engineering distinction:** pause behavior is a *clip policy*, not necessarily a mandate to stop all audio. For the originating short-clip joke mod, the owner prefers **allowing an already-playing sub-4-second clip to finish through a normal pause**, without resuming/restarting it later; stop/error cleanup for scene exit, actual interruption and clip ownership still matters. This is **a project design decision, not a verified game requirement or a tested v0.0.10 behavior**. In a different mod with long looping/position-dependent audio, pause suspension may be appropriate. Avoid repeatedly re-engineering pause handling when it adds more audible discontinuity than a short clip finishing on its own. The old diagnostic still suspends on Escape.

**Evidence boundaries:** earlier full game-speed drift under Probe 013 remains unresolved; 014's approximately 40-ms HUD sampling and fractional interpolation are heuristics, not a native presented frame clock. Calibration by visual judgment is useful, but does not prove cast animation begins at the exact buff tick. Retain separate tests for death, end-of-Rage cleanup, scene teardown and optional multi-unit overlap.

## Bounded PCM16 file-backed voices: owner runtime pass in TFM2 0.6.3 (2026-10-13)

**Status: OWNER RUNTIME-VERIFIED PARTIAL PASS; supersedes the earlier CI-only status below.** Berserker Keeps Yelling **Probe 015 / mod v0.0.11** was physically run by the owner inside **Teamfight Manager 2 stable 0.6.3, host/SDK ABI 9**, after Linux Rust synthetic tests and Windows compile/generate/decode CI had passed. The owner **heard the actual short WAV files start with Rage, stop when Rage expired, continue through Escape/pause, and stop upon title exit**. A faster playback speed audibly made the WAV stop sooner in real time, as expected for the projected Rage state.

**Observed runtime evidence:** one `RAGE_WAV_ARM samples=2 phase_lead_ticks=0`, **13 WAV starts**, **11 ordinary projected Rage-end stops** with successful WinMM reset, **one WAV naturally completing during an Escape pause**, **one successful active-WAV stop on title exit**, **two pause/resume pairs**, and **zero WAV asset/play/stop errors** in the owner's bounded run. All observed WAV starts in this visible playback segment belonged to one Berserker instance, so **simultaneous separate champion playback was not verified**.

**Generalizable tested implementation direction:** use strict, bounded RIFF PCM16 WAV validation (mono/stereo, 8–48 kHz, 0.1–4 s, max 2 MB each), **owned independently stoppable WinMM waveOut buffers**, event-to-voice identity tracking and explicit scene cleanup. The existing per-voice stop behavior was confirmed in prior manual Probe 008; Probe 015 now establishes that **external WAV-file payloads** can be played and reset during real TFM2 0.6.3 replay. For short audio, the chosen behavior is to **allow an already-started clip to finish through an ordinary pause**, with no new starts until HUD advances and no duplicate replay of the served clip on resume. This is valid for this mod's short-clip policy, **not a universal recommendation for long or spatial game sounds**.

**Evidence boundaries:** the trigger is still a **watched-presimulation `berserker_skill1` buff interval projected through an estimated visible HUD time**, **not a verified native Rage/cast animation callback or exact replay clock**. Faster wall-clock stop is consistent with Rage-linked end, but no controlled higher-speed event-time measurement proves frame accuracy. Two later presimulation unit disappearances with Rage-like buff active had last-known `alive=true` and nonzero HP: **not verified death**, so they must not automatically trigger death punchlines. No evidence here establishes in-game master-volume mapping, true simultaneous Berserker files, rewind/seek, force unload or completion/continuation for clips shorter than Rage. This prototype plays **one file per Rage**; continuous audio coverage from shorter production clips remains a separate implementation step.

## Probe 016 short-file handoff and death-correlation distinction

**STATUS: OWNER RUNTIME VERIFIED PARTIAL PASS (2026-10-13; TFM2 stable 0.6.3 / ABI 9, mod v0.0.12).** This builds on the prior physically verified v0.0.11 file playback and now closes the ordinary short-file continuation gate.

A small, per-entity **bounded continuation state machine** tracks whether the current file is playing, completed, waiting through pause, or ready for the next different sample. It rotates away from the previous clip where multiple files exist, caps extreme short-clip churn, does not start new audio while HUD time is paused, and resets state on projected Rage end/scene change. In the owner run, the user reported **no audible gaps, no overlap, and correct cutoff at Rage expiration**. The bounded log recorded **41 WAV starts, 20 natural file completions, 20 same-Rage continuations, 21 successful Rage-end stops and zero WAV error markers**. This is runtime evidence that short file completion can hand off to a different owned WAV during the same projected Rage interval. Under a one-file bank, the design still intentionally avoids replaying that same clip merely because a pause ended.

**Important reusable death-evidence warning:** a watched-simulation record of a unit **disappearing while its last observed `is_alive` was true and HP was positive** is **not** a death callback. Even a later **same team/name and new entity ID** appearance is only a lifecycle correlation, not a demonstrated death/respawn cause. The project added bounded observation-only same-name/team reappearance diagnostics, while separately preserving same-ID **alive→dead** observations if they occur; **no death-punchline audio triggers** in this stage. Confirming that a presented death occurred—and whether it preempted Rage—remains the independent evidence requirement.

## Stable player KDA counters versus disappearing champion entities — Probe 017 (runtime observation, 2026-10-13)

**Status: OWNER-GAME RUNTIME VERIFIED for KDA death-count changes coinciding with disappearing champion entities (TFM2 0.6.3 / SDK-host ABI 9 / Berserker mod v0.0.13); Rage-active death and presentation-time audio remain unverified.** The [stable API reference](https://github.com/teamsamoyed/TeamfightManager2Mod/blob/main/docs/stable-api-reference.md) exposes `StableSim::player_count/player_at`, `StablePlayer::id/team/champion/is_alive/deaths`, and champion buff reads. Player `deaths()` is documented as a *match KDA counter*. It is a different observation surface from champion `StableEntity::is_alive` or absence from `entity_at` iteration. The SDK also exposes `kill_log_count/kill_log_at`, but that has **not** been exercised by this probe.

The Berserker project **implemented and owner-tested** a read-only observer using its previously version-gated watched `ClientMatchView` simulation, with a pure per-player counter-difference tracker. The design preserves known Berserker player identity across an absent `champion()` view and reports a `deaths()` increase only after two readings in the **same session**, never treating positive-HP disappearance or a newly allocated champion entity ID as proof of death. A single death increment plus identical player/team, adjacent simulation ticks, and a prior alive champion with `berserker_skill1` receives a **prior-Rage-candidate** classification; missing intervening samples, counter jumps, team changes or delayed increments are **unresolved**. Independently verifying `berserker_skill1` as Rage is still required.

**Limitations:** A KDA delta in watched presimulation is *not* a callback on the visible replay frame, nor confirmation of precisely when a death-only audio punchline should interrupt playback. The original-game owner run establishes the player KDA death-count changes in the watched simulation; it does **not** establish death at a corresponding rendered replay frame. The existing Candidate-A native detour may conflict with another mod detouring the same target; Probe 017 adds **no second detour**. No gameplay changes or audio death stingers are part of this diagnostic.

**Owner-run reusable observation:** A single Berserker player (stable ID 2) had exactly two one-count KDA increases, at watched simulation ticks **13,363** and **44,487**. Both coincided **on the same ticks** with champion entity disappearance; immediately preceding entity snapshots still said alive with **positive HP**. New champion IDs later appeared for the same roster slot. Therefore prior entity `is_alive=true` and positive HP **do not disprove actual player death** at an observed deletion, but a bare disappearance without an independent player death-counter increase remains ambiguous. This supersedes uncertainty for **these two events only**, not all despawns. Both deaths had `berserker_skill1` absent in the immediately previous tick: **two successful non-Rage negative controls**, **zero Rage-active death samples**, and **no punchline**. The watched simulation was ahead of the visible HUD, so the exact presented death moment is still unknown.

## Projected death priority from player KDA and prior-tick buff — Probe 018 (source only, 2026-10-13)

**STATUS: TEST DESIGN AND SOURCE IMPLEMENTED; no physical runtime pass and no executed synthetic CI tests yet.** Scoped to the Berserker project on TFM2 **0.6.3 / stable host ABI 9**, mod **v0.0.14**. The owner-verified Probe 017 player-KDA death source is the **input**, not fresh evidence that a Rage death has been observed.

A practical generic pattern for read-only, presim-ahead mods is a **session-scoped bounded marker ledger** for events that have independent provenance (such as an adjacent `StablePlayer::deaths()` increase), followed by a **separate HUD-projected event decision**. This preserves the distinction between *simulation tick* and *presented event time*. For Rage-only death eligibility, require both: a one-count same-player/team adjacent-tick KDA change, and matching *previous champion entity* Rage presence at `death_tick - 1`. In a same-tick death/buff-disappearance case the earlier Rage state is what matters; the current tick's lack of buff does not prove ordinary expiry. That rule is presently a **synthetic design hypothesis**, not an owner-verified Rage death.

**Negative controls:** Probe 017's two owner-run KDA deaths both followed Rage expiration and must never authorize the stinger. **Fail-closed rules:** different session, missing prior entity, ambiguous counter jump, contradictory Rage state, retained ledger overflow, rewind/seek or unsupported replay-clock mapping cannot authorize death audio. A hidden marker alone never implies exact visible-frame timing.

The originating mod prepared a silent `would_preempt_rage` classifier, bounded marker store and tests for hypothetical death-during-Rage, coincident expiry, duplicate poll and negative controls. The GitHub Actions runs **failed before runner allocation** (empty step lists and runner ID zero), so **source/testing fixtures are prepared only**; no executed CI or original-game validation is claimed. The existing WAV chaining is unchanged and no death punchline fires. Test with installed SDK and the 0.6.3 client before considering any real audio preemption.

## Replay seek into an active buff interval with no owned audio — source-level safety pattern (2026-10-14)

**Status: SOURCE REVIEW / UNEXECUTED SYNTHETIC REGRESSION; original-game replay seek NOT VERIFIED.** Relevant to audio mods that project presimulation state into visible playback. Origin: [Berserker Keeps Yelling](https://github.com/patrickehopkins/TFM2-Berserker-Keeps-Yelling), `src/replay_preview.rs`, `docs/DESIGN.md`, and `docs/TEST-PLAN.md`, 2026-10-14. **Current target:** game 0.6.4 / stable SDK ABI 10 (mod v0.0.15 migration pending original-game pass). **Failure case to test:** seeking into a time range where an observed Rage-like buff is active can skip the presentation/audio activation entirely.
