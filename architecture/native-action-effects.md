# Native action timing and effect execution — TFM2 0.6.3

**Status: STATIC EVIDENCE for native action paths; RUNTIME VERIFIED only for original champion Knight W acceptance/effect timing.**  
**Origin:** Creep Chaos Probes 010F, 010G-3, 010H, 010J, **corrective Probe 010K-4**, offline clone classification **010L-4**, **010M-1** static selector contrast, **010M-2** kind-dispatch verification, **010M-3** spatial-callee follow-up, and **010N-1** native caller topology, studied 2026-10-08 to 2026-10-10. Full traces and standalone verifiers remain in the originating mod repository. This summary does **not** establish executable champion skills on native creeps.

**Exact Windows build constraint:** Teamfight Manager 2 **0.6.3**, original game EXE SHA-256 `f21cf691799a83d9afa0ccae3e2b95862f5780446a501ee97860b91b752dbe2f`; PE timestamp `0x6AC5C567`; SizeOfImage `0x052D6000`. These are **native addresses and offsets, not SDK-stable ABI**. Re-identify instructions, jump tables, ownership and field layout for every other build.

## What has been established

The game has an original per-entity action representation, native cached refcounted effect specifications, and an **original 0x38-byte ready-effect vector** local to the simulation-state processor. Different entity kinds can generate records into that common final effect pipeline. The native callback is an effect-object virtual method **`vtable+0x20`** called in original simulation code at VA **`0x1416FB44F`**.

- **Ordinary native kind-3 lane-minion attack (STATIC):** its original action slot A (`entity+0x568/+0x570`) has an active-action/timing path which constructs a ready record from its cached slot-A effect spec (`entity+0x488`) at VA **`0x1416F8372–0x1416F83DA`**, via original append helper **`0x1416E8730`**. Its runtime action is a concrete `target_attack` type, but the melee action's vtable and effect callback are **not** identical to a champion's identically named attack. The ready records are processed through the same effect-object dispatcher as champion effects.
- **Original kind-15 champion Knight W (STATIC):** the accepted *deferred* W action-start route sets `entity+0x70=5`, initializes **progress `entity+0x78=0`**, and stores a native **24-byte tagged target at `entity+0x88..+0x9F`**. This target is prepared by original helper VA **`0x14140A6A0`**, which copies targets of tag other than 2 and may clamp position-tag 2 relative to caster coordinates and range.
- **Original champion W timed effect (STATIC):** kind-15 action state 5 selects slot C W at VA **`0x1416F7F68`**. The original W-specific branch **`0x1416F7FF6` unconditionally jumps to `0x1416FAEE3`**, where effect timing is calculated. The comparison at **`0x1416FAF0D`** uses **actual W progress `entity+0x78`**. On phase equality, the original effect is retained/refcounted, source identity `entity+0x5B8` and the target **from the same `+0x88..+0x9F` region** are packaged; VA **`0x1416FAF7A`** appends a genuine ready-effect record via `0x1416E8730` for original callback dispatch.
- **Original W progress and completion (STATIC):** the same native simulation-state function dispatches kind 15 again (kind update jump table RVA **`0x03BB40BC`**), and its state-5 update branch at VA **`0x1416FD3F1–0x1416FD3F8`** **increments `entity+0x78`**, compares against a native calculated completion duration and, on completion, reaches **`0x1416FD44D`** which resets action state 5 to 0. This is a **normal action-duration completion route**, not proof of death/cancellation semantics.
- **Conditional alternate scheduler (STATIC):** the original champion W action-entry method also contains a separate original condition-controlled path which can enqueue a refcounted effect in an entity-owned 0x38-byte **pending countdown queue** at `entity+0x2A0/+0x2A8/+0x2B0`. This **is not the only native W path**. The common effect processor can consume such records, including in kind-3 processing; that consumer reachability **does not prove a minion can legitimately produce W records**.
- **Original entity action and pending-effect lifetime (STATIC):** native entity cloning uses action-specific clone methods for five action slots and retains cached effects; a full entity clone duplicates pending effect records into independent queue storage with retained effect-object references. Common entity teardown releases those objects. A stored vtable address alone is therefore not a safe ability installer.

- **Additional full entity-array action-clone path (STATIC, Probe 010L-4; 2026-10-10):** offline disassembly from the exact-build-fingerprinted user scan shows native RVA **`0x01071BD0`** obtaining a source array pointer and multiplying a record count by **`0x6B8`**, reading source slot-C action data/vtable `+0x588/+0x590`, invoking the action's **vtable `+0x48` clone**, then copying the prepared C cached-effect/tag `+0x4F8/+0x528` and the cloned action pair to corresponding offsets in an **indexed destination record**. Nearby writes cover the rest of the native action set and other entity data. This clarifies an ambiguous 010L-3 “potential setter” as **another deep-clone/array assembly path, not a live kind-3 ability installer**. A local verifier checked **27/27 exported instruction/report anchors**, but the original EXE was not independently rescanned in the review environment and the caller/simulation-copy context is **unmapped**. Never infer that copying existing owned actions creates a new ability or authorizes minion use.

## Kind-3 action selection versus champion W — additional offline scope (Probe 010M-1, 2026-10-10)

**STATIC EVIDENCE / NEGATIVE WITHIN FIVE SELECTED FUNCTION BODIES — NOT A GAMEPLAY TEST.** Creep Chaos's user-executed, SHA-gated 0.6.3 Win64 offline report examined five previously mapped native functions. The report fingerprint matches the pinned EXE (SHA-256 `f21cf691799a83d9afa0ccae3e2b95862f5780446a501ee97860b91b752dbe2f`, timestamp `0x6AC5C567`, SizeOfImage `0x052D6000`); 43 selected assembly anchors and explicit reference counts were independently checked **against the report, not original EXE bytes**. No new native hook or kind-3 cast was attempted.

- Two **kind-3-aware combat-decision functions**, RVAs `0x00EB31C0` and `0x00ED04F0`, repeatedly read the real original **slot-A action `entity+0x568/+0x570`**, its cache and timing methods. The second function contains no B/C/D-offset candidates in the surveyed `.pdata` body. The first has two incidental **untyped, non-paired** B/D-like displacements using a different register near its end; they are **not evidence of additional skill selection**. Importantly, their early `kind==3` comparisons operate on **enumerated entities**, not independently proven acting-minion pointers.
- Original **kind-3 state writer** RVA `0x01414180` resolves a genuine kind-3 entity, writes native `entity+0x70=0/1` with associated target/state, and consults **slot A `+0x80`** to prepare a native simulation event. No B/C/D action references were identified in this surveyed native function. That event is **not synonymous with the ready-effect vector**.
- Original **champion W entry** RVA `0x016F4450` uses **slot C** but requires **kind 15** before its real W state-5 start. The **shared** processor RVA `0x016F6CC0` has both kind-3 **slot-A** handling and the separate champion **slot-C/state-5** W route. All-slot references in that entire mixed-kind function must **not** be mistaken for kind-3 reachability.

**Conclusion and limitation:** No original native B/C/D choice, independent cooldown, or kind-3 champion W progression has been demonstrated in those surveyed branches. This **does not globally disprove** other native action dispatchers or establish that a mod must duplicate champion abilities. A separate **MC-owned deterministic chooser that delegates genuine owned native abilities** is only a **design hypothesis**, not a discovered API. **Follow-up resolved in 010M-2:** both native kind effect/update table entries were extracted, and the previously unmapped kind-3 update destination is RVA `0x016FCE25`; see the next section. This does **not** establish additional minion ability selection. Origin: Creep Chaos `docs/PROBE-010M1-SELECTOR-STATIC-FINDINGS.md`. Keep detailed report and raw disassembly only in the originating project's private investigation.

## Kind-3 spatial pre-state processing — 010M-3 (2026-10-10)

**STATIC OFFLINE FINDING; negative for skill selection in one native callee.** In the exact-build TFM2 0.6.3 Win64 user-generated `probe010m3-prestate.json` report (original EXE SHA-256 `f21cf691799a83d9afa0ccae3e2b95862f5780446a501ee97860b91b752dbe2f`, timestamp `0x6AC5C567`, SizeOfImage `0x052D6000`), the function at **RVA `0x01415B40`** was decoded as **445 instructions** (`0x01415B40..0x01416410`); the uploaded bounded excerpt contained **227 instructions**, no truncation. **All 12** native-field-looking references at `+0x68/+0x70/+0x78/+0x80` are actually **`rsp`-based stack locals**, not reads or writes of a native entity's kind/state/progress. No direct A/B/C/D action-pair or cached skill-effect fields are identified in this entire scoped function.

The function retrieves coordinates at `+0x658/+0x660` from looked-up objects, iterates candidate entries, compares coordinates, squares both differences, sums them and compares with a squared threshold. Its conditional callbacks and event-like builder at **RVA `0x01703970`** are *not yet assigned specific gameplay semantics*. This supports **spatial/proximity candidate checking**, **not** an existing minion ability chooser. For contrast, the paired **RVA `0x01414180`** genuinely reads original minion action A and kind/state on nonstack entity bases. The user report is the evidence source, **not an independently repeated EXE scan or physical gameplay test**.

**Preserved negative result:** Do not infer that a callee's role is skill scheduling just because it precedes a known action state writer; verify *object-pointer provenance* and actual effects of nested callbacks. Conversely, rejecting this callee does **not** globally prove absence of native kind-3 B/C/D skill selection. For an MC that may ultimately supply its own deterministic chooser, legitimate game-owned action construction, cached-effect lifecycle and simulation-copy authority remain separate blockers. The originating Creep Chaos report is `docs/PROBE-010M3-SPATIAL-CALLEE-FINDINGS.md`; the planned next static study is the **original constructor/clone/spec-refresh direct-caller graph** (not a verified native insertion point). Do not publish raw disassembly or personal paths.

## Native entity constructor and action-cache caller topology — 010N-1 (2026-10-10)

**STATIC OFFLINE EVIDENCE; not a kind-3 skill installer.** Creep Chaos Probe 010N-1 scanned the original TFM2 **0.6.3 Win64** executable (user's SHA/PE-gated direct-call scanner, reported SHA-256 `f21cf691799a83d9afa0ccae3e2b95862f5780446a501ee97860b91b752dbe2f`, PE timestamp `0x6AC5C567`, SizeOfImage `0x052D6000`). The bounded JSON report covers **154,191** file-backed `.pdata` functions and **13,747,032** decoded instructions; the original EXE itself was **not independently rescanned** in the review environment. The scanner recognizes **direct-immediate native calls only** and therefore cannot conclude anything from the absence of indirect/virtual factory calls.

- The original lane-minion constructor **RVA `0x013F9880`** has **12 direct call sites, all within caller RVA `0x013FAB90`**. Their three stack arguments cover the full observed **2 × 3 × 2** matrix: `[rsp+0x38]` ∈ {0,1}, `[rsp+0x28]` ∈ {0,1,2}, and `[rsp+0x20]` ∈ {0,1}. **Parameter game meaning is unknown.** Eight call sites immediately pass the resulting local record to **RVA `0x0140B6C0`**; the remaining four show nearby explicit **`0x6B8` entity-stride** collection assembly. This identifies a **construction/handoff research target**, not a verified owner insertion API or primary-simulation hook.
- An authentic four-action champion constructor **RVA `0x0140A850`** has one direct caller (**RVA `0x01416410`**), a useful contrast with minion construction.
- The native default initializer **RVA `0x017263D0`** has **37** direct sites across **19** caller functions. The single-entity deep clone **RVA `0x0149CA90`** and cached-effect refresh **RVA `0x01701360`** each have **32** direct sites (12 and 11 unique caller functions respectively). **Six functions** (`0x013E1FA0`, `0x013E2980`, `0x013E54B0`, `0x013E8380`, `0x013EA0F0`, `0x013FF300`) contain **both clone and refresh calls**, often with comparable counts. In the `0x013E8380` caller, paired clone/refresh sites are separated by only a few instructions; **same-object ownership, real execution order across branches, and authoritative copy/fan-out are unproved**.
- Full entity-array clone **RVA `0x01071BD0`** has two direct calls from **RVA `0x0148C220`**, which also directly calls a single-record clone. Treat this as a **simulation-copy investigation lead**, not proof that it duplicates workers or accepts new action definitions.
- Zero direct matches for the original **Knight W factory `0x01279530`** and **melee minion attack factory `0x014DD6A0`** are **expected from virtual factory dispatch** already established in prior probes. These are **negative coverage controls**, not evidence the factories are unused.

**Reusable lesson:** Identify **constructor sources, call-site parameter combinations, record ownership, cloned action objects and cached effect-spec refresh** separately. Static direct-call co-occurrence is neither a live ability-slot setter nor proof of a deterministic simulation-insertion boundary; verify exact object provenance, lifecycle and worker copies before writing anything. The proposed follow-up is a bounded read-only analysis of **RVA `0x0140B6C0`** and the twelve-way caller alongside a known champion constructor and clone/refresh control. That analysis is **prepared only, not yet tested**. Originating detailed record: Creep Chaos `docs/PROBE-010N1-OWNERSHIP-TOPOLOGY-FINDINGS.md`. No original EXE, raw report, local paths or third-party assets are included.

## Physical observations versus code-path proof

Creep Chaos **v0.0.18** Windows Probe 010J physically recorded **78 watched original Knight W attempt entries**, **50 native W cooldown commitments**, and **50 genuine native W shield callbacks exactly 12 simulation ticks after commitment**. During the synchronous W-start observation, the watched entity had **pending queue length 0 before/after and capacity 0 on all 78 attempts**. This is *consistent with* the separate native active-action ready-effect path; it **does not** prove every observed cast's specific branch/phase or a visible replay timestamp. The prior v0.0.17 observer returned zero apparent appends because it collapsed multiple outcomes; this was an **instrumentation false negative**, not evidence that native W effects failed.

## Important negative result — misidentified W target/progress fields

**REJECTED / SUPERSEDED 2026-10-09:** an earlier Creep Chaos static report assigned block **`0x1416F88D2–0x1416F896A`** to Knight W and consequently described W progress as `entity+0xA0` and W effect-time target at `entity+0xA8..+0xBF`. Although its opcode assertions passed, **the required control-flow edge was wrong**. The real W branch at `0x1416F7FF6` jumps to **`0x1416FAEE3`**, and original W consistently uses **`+0x78` progress and `+0x88..+0x9F` target** from start to effect. The other block exists but its action/variant ownership is **not classified** by these studies. This is an example of why instruction-byte verification alone does not prove a semantic call path.
